## Що зараз зроблено в незакомічених змінах

Цей `README.md` описує саме поточний незакомічений стан робочого дерева відносно `HEAD`, а не попередню закомічену версію проєкту.

Головна ідея змін: ти перетворював один NestJS-проєкт у невеликий fullstack-набір з трьох контейнерів:

- `app` для NestJS API;
- `db` для MySQL;
- `web` для nginx, який віддає статику й проксіює API.

Паралельно ти виніс бекенд у підпапку `backend/`, додав окремий React-фронтенд у `frontend/`, зібраний build поклав у `client/`, а запуск через Docker переписав під нову структуру.

## Повний список того, що ти робив

### 1. Переніс бекенд у `backend/`

Майже весь початковий NestJS-код із кореня проєкту переїхав у `backend/`:

- `package.json` -> `backend/package.json`
- `package-lock.json` -> `backend/package-lock.json`
- `tsconfig.json` -> `backend/tsconfig.json`
- `ormconfig.ts` -> `backend/ormconfig.ts`
- `src/**` -> `backend/src/**`
- `test/**` -> `backend/test/**`
- службові конфіги (`eslint`, `prettier`, `nest-cli`) також переїхали в `backend/`

Що це означає:

- корінь репозиторію тепер став місцем для orchestration-рівня;
- сам NestJS-проєкт тепер живе окремо всередині `backend/`;
- така структура зручніша, коли поруч з API з'являються фронтенд, nginx, docker-конфіги та інші сервіси.

### 2. Переніс наявні бекендові можливості без зміни логіки

Разом із переносом у `backend/` ти не переписував основну бізнес-логіку, а переніс її як є:

- `auth`-модулі;
- `tables`-модулі;
- `typeorm`-конфігурацію;
- `shared`-шар;
- `ormconfig.ts`;
- `main.ts`, `app.module.ts` та інші базові файли NestJS.

Це важливо, бо поточні незакомічені зміни в основному про структуру проєкту й інфраструктуру, а не про нову бізнес-логіку бекенда.

### 3. Вирівняв конфіги TypeScript після переносу в `backend/`

`tsconfig.build.json` у корені видалений, а новий `backend/tsconfig.build.json` створений вже поруч із `backend/tsconfig.json`.

Що це означає:

- бекенд тепер повністю самодостатній усередині `backend/`;
- збірка більше не залежить від старого кореневого розташування файлів;
- TypeScript-конфіги відповідають новій структурі директорій.

### 4. Підправив e2e-тест після переносу

`backend/test/app.e2e-spec.ts` змінив імпорт `AppModule` на шлях відносно нової папки:

```ts
import { AppModule } from '../src/app.module';
```

Навіщо це потрібно:

- після переносу `test/` в `backend/test/` старий імпорт уже не підходив;
- e2e-тест повинен бачити модуль у новому місці.

### 5. Оновив lockfile після переносу та встановлення залежностей

`backend/package-lock.json` не просто переїхав, а ще й був оновлений під час локальної роботи із залежностями.

Що це означає:

- ти, ймовірно, запускав `npm install` уже в новій структурі;
- lockfile зафіксував стан пакетів у `backend/`;
- це технічна зміна інфраструктурного рівня, а не зміна прикладної логіки.

### 6. Переписав `Dockerfile` під нову структуру

`Dockerfile` більше не збирає старий кореневий Nest-проєкт. Тепер він:

- бере `backend/package.json`, а не кореневий `package.json`;
- ставить production-залежності;
- глобально ставить `@nestjs/cli`;
- більше не копіює `dist`.

Що це означає на практиці:

- контейнер готує runtime-середовище саме для `backend/`;
- код не вбудовується в образ на етапі `COPY dist`, а приходить через volume-монтування з `docker-compose.yml`;
- запуск зміщується від старого production-варіанта до більш "розробницького" сценарію всередині контейнера.

### 7. Сильно змінив `docker-compose.yml`

Основні зміни:

- у `app` додано volume `./backend:/app`;
- додано окремий volume для `/app/node_modules`;
- прямий проброс порту `3001` закоментований;
- команда запуску змінилась на `npm run migration:run && npm run start`;
- для `db` проброс порту `3307:3306` теж закоментований;
- додано новий сервіс `web` на `nginx:alpine`;
- `web` віддає зібраний frontend із `client/`;
- `web` використовує `nginx.conf` і проксіює API до `app`.

Що це означає:

- Nest запускається всередині контейнера прямо з коду, змонтованого з `backend/`;
- міграції виконуються перед стартом сервера;
- база може бути внутрішнім сервісом docker-мережі без прямого відкриття назовні;
- назовні віддається лише nginx на `80` порту.

### 8. Додав `nginx.conf`

Цей конфіг робить дві ключові речі:

- віддає SPA-сторінки зі зібраного frontend-build;
- проксіює запити `/api/` на сервіс `app:3001`.

Навіщо це потрібно:

- фронтенд і API можуть працювати під одним хостом;
- не треба окремо думати про CORS для браузера в такому сценарії;
- nginx стає єдиною точкою входу.

### 9. Додав окремий frontend у `frontend/`

У репозиторії з'явився React-проєкт у `frontend/`.

По тому, що видно зараз:

- це застосунок на `react-scripts`;
- доданий `axios`;
- у `frontend/src/App.js` є простий запит на `/api/tables`;
- отримані дані рендеряться на сторінці.

Що це означає:

- тепер є окремий клієнт для перевірки API;
- клієнт уже орієнтується на nginx-проксі через шлях `/api/...`;
- фронтенд і бекенд почали працювати як одна зв'язка.

### 10. Додав зібрану статику в `client/`

У `client/` лежить готовий build фронтенда:

- `index.html`
- `asset-manifest.json`
- `static/js/*`
- інші стандартні файли build-артефактів

Навіщо це потрібно:

- nginx монтує саме `client/` у `/usr/share/nginx/html`;
- отже `web` контейнер віддає вже зібрану статику, а не сирцевий React-код;
- це простий варіант деплою SPA через nginx.

### 11. Підняв локальні docker-артефакти

У робочому дереві також є локальні/generated каталоги:

- `backend/dist/`
- `backend/node_modules/`
- `mysql_db/`
- багато файлів усередині `frontend/node_modules/`

Що це таке:

- це не нова бізнес-логіка;
- це наслідок локальної збірки, встановлення залежностей і запуску контейнерів;
- `mysql_db/` містить реальні дані MySQL із volume.

Навіщо це з'явилось:

- `backend/dist/` з'являється після build;
- `node_modules/` з'являються після `npm install`;
- `mysql_db/` створюється через bind mount `./mysql_db:/var/lib/mysql`.

## Пояснення кожного непорожнього рядка `Dockerfile`

Поточний вміст:

```dockerfile
FROM node:20-alpine

LABEL maintainer='Some DEV'

RUN mkdir /app
WORKDIR /app

COPY backend/package.json ./
RUN npm i --production
RUN npm i -g @nestjs/cli
```

1. `FROM node:20-alpine`
   Базовий образ із Node.js 20 на Alpine Linux. Він дає готове легке середовище для запуску Node/Nest усередині контейнера.

2. `LABEL maintainer='Some DEV'`
   Додає метадані до Docker-образу. Це інформаційний рядок про автора або відповідального за образ.

3. `RUN mkdir /app`
   Створює каталог `/app`, у якому далі житиме застосунок усередині контейнера.

4. `WORKDIR /app`
   Робить `/app` поточною робочою директорією. Усі наступні команди виконуються вже відносно неї.

5. `COPY backend/package.json ./`
   Копіює в контейнер саме `backend/package.json`, бо бекенд більше не лежить у корені репозиторію.

6. `RUN npm i --production`
   Встановлює тільки production-залежності. Це зменшує образ і показує, що контейнер не розрахований на повний dev-набір пакетів.

7. `RUN npm i -g @nestjs/cli`
   Глобально ставить Nest CLI, щоб можна було виконувати `npm run start`, навіть якщо `@nestjs/cli` не потрапляє в локальні production-залежності.

## Пояснення кожного непорожнього рядка `docker-compose.yml`

Поточний вміст:

```yaml
services:
  app:
    build:
      context: .
    env_file:
      - .env
    volumes:
      - ./backend:/app
      - /app/node_modules
#    ports:
#      - "3001:3001"
    depends_on:
      db:
        condition: service_healthy
    command: >
      sh -c "npm run migration:run && npm run start"
  db:
    image: mysql:8
    volumes:
      - ./mysql_db:/var/lib/mysql
    environment:
      - MYSQL_DATABASE=my-nestjs-test
      - MYSQL_USER=user
      - MYSQL_PASSWORD=user
      - MYSQL_ROOT_PASSWORD=superpass
#    ports:
#      - "3307:3306"
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "user", "-psuperpass"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 5s

  web:
    image: nginx:alpine
    ports:
      - "80:80"
    depends_on:
      - app
    volumes:
      - ./client:/usr/share/nginx/html
      - ./nginx.conf:/etc/nginx/conf.d/default.conf
```

1. `services:`
   Починає секцію всіх сервісів, які керуються через Docker Compose.

2. `  app:`
   Оголошує сервіс бекенда.

3. `    build:`
   Починає опис того, як збирати образ для `app`.

4. `      context: .`
   Каже збирати образ із кореня репозиторію, де лежить `Dockerfile`.

5. `    env_file:`
   Починає список файлів зі змінними оточення для контейнера.

6. `      - .env`
   Підключає `.env` у контейнер `app`, щоб бекенд бачив налаштування БД, JWT та інші змінні.

7. `    volumes:`
   Починає секцію монтування директорій і томів.

8. `      - ./backend:/app`
   Монтує локальну папку `backend/` в `/app` усередині контейнера. Завдяки цьому контейнер працює з реальним кодом бекенда з репозиторію.

9. `      - /app/node_modules`
   Створює окремий volume для `node_modules`, щоб залежності контейнера не затиралися bind mount-ом із хоста.

10. `#    ports:`
    Закоментована секція пробросу порту для `app`. Це означає, що прямий доступ до Nest з хоста поки вимкнений.

11. `#      - "3001:3001"`
    Закоментований проброс порту `3001`. Ймовірно, ти вирішив віддавати доступ до API через nginx, а не напряму.

12. `    depends_on:`
    Починає секцію залежностей сервісу `app`.

13. `      db:`
    Вказує, що бекенд залежить від сервісу бази даних.

14. `        condition: service_healthy`
    Дозволяє старт бекенда лише після того, як `db` пройде healthcheck і стане готовою.

15. `    command: >`
    Починає багаторядковий YAML-рядок для команди запуску контейнера.

16. `      sh -c "npm run migration:run && npm run start"`
    Усередині контейнера спочатку запускає міграції, а потім стартує Nest. Якщо міграції впадуть, сервер не запуститься.

17. `  db:`
    Оголошує сервіс MySQL.

18. `    image: mysql:8`
    Використовує готовий офіційний образ MySQL 8.

19. `    volumes:`
    Починає секцію volume-монтувань для MySQL.

20. `      - ./mysql_db:/var/lib/mysql`
    Зберігає файли бази в локальній папці `mysql_db`, щоб дані не зникали після перезапуску контейнера.

21. `    environment:`
    Починає секцію змінних оточення для ініціалізації MySQL.

22. `      - MYSQL_DATABASE=my-nestjs-test`
    Каже контейнеру створити базу `my-nestjs-test`.

23. `      - MYSQL_USER=user`
    Каже створити користувача `user`.

24. `      - MYSQL_PASSWORD=user`
    Встановлює пароль для користувача `user`.

25. `      - MYSQL_ROOT_PASSWORD=superpass`
    Встановлює пароль root-користувача MySQL.

26. `#    ports:`
    Закоментована секція пробросу порту MySQL назовні.

27. `#      - "3307:3306"`
    Закоментований доступ до MySQL із хоста через порт `3307`. Тобто база зараз задумана як внутрішній docker-сервіс.

28. `    healthcheck:`
    Починає секцію перевірки стану контейнера MySQL.

29. `      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "user", "-psuperpass"]`
    Команда, якою Docker перевіряє, чи жива база і чи готова відповідати.

30. `      interval: 5s`
    Перевірка виконується кожні 5 секунд.

31. `      timeout: 3s`
    Якщо за 3 секунди відповіді немає, конкретна перевірка вважається невдалою.

32. `      retries: 10`
    Після 10 невдалих спроб сервіс вважається unhealthy.

33. `      start_period: 5s`
    Дає контейнеру 5 секунд на старт перед тим, як жорстко оцінювати healthcheck.

34. `  web:`
    Оголошує третій сервіс, який працює як фронтовий веб-шар.

35. `    image: nginx:alpine`
    Використовує легкий nginx-образ на Alpine Linux.

36. `    ports:`
    Починає секцію пробросу портів для nginx.

37. `      - "80:80"`
    Відкриває порт `80` контейнера на порт `80` хоста. Саме через нього користувач заходить у застосунок.

38. `    depends_on:`
    Починає опис залежностей `web`.

39. `      - app`
    Показує, що nginx повинен стартувати разом із сервісом бекенда, на який він проксіює API.

40. `    volumes:`
    Починає секцію монтувань для nginx.

41. `      - ./client:/usr/share/nginx/html`
    Монтує зібрану фронтенд-статику в стандартну папку, з якої nginx віддає HTML, JS, CSS та інші файли.

42. `      - ./nginx.conf:/etc/nginx/conf.d/default.conf`
    Підміняє стандартний конфіг nginx власним файлом, у якому налаштовані SPA-router і проксі на API.

## Пояснення кожного непорожнього рядка `nginx.conf`

Поточний вміст:

```nginx
server {
    listen 80;
    server_name localhost;
    index index.html;
    root /usr/share/nginx/html;

    location / {
        try_files $uri$args $uri$args/ /index.html;
    }
    location /api/ {
        proxy_pass http://app:3001/;
        proxy_set_header Host $host;
    }
}
```

1. `server {`
   Починає блок конфігурації одного віртуального хоста nginx.

2. `listen 80;`
   Каже nginx слухати HTTP-запити на 80 порту всередині контейнера.

3. `server_name localhost;`
   Вказує ім'я хоста, для якого застосовується цей конфіг. У локальному середовищі це `localhost`.

4. `index index.html;`
   Каже, що файлом за замовчуванням у директорії буде `index.html`.

5. `root /usr/share/nginx/html;`
   Встановлює кореневу папку, з якої nginx віддає статичні файли фронтенда.

6. `location / {`
   Починає правило для всіх звичайних запитів до фронтенда.

7. `try_files $uri$args $uri$args/ /index.html;`
   Nginx спочатку намагається знайти реальний файл або папку, а якщо не знаходить, віддає `index.html`. Це потрібно для SPA-маршрутизації React-застосунку.

8. `}`
   Закриває блок `location /`.

9. `location /api/ {`
   Починає окреме правило для всіх запитів, що йдуть на API.

10. `proxy_pass http://app:3001/;`
    Пересилає запити `/api/` у контейнер `app` на порт `3001`, де працює NestJS.

11. `proxy_set_header Host $host;`
    Передає у проксійований запит оригінальний заголовок `Host`, щоб бекенд бачив, з якого хоста прийшов запит.

12. `}`
    Закриває блок `location /api/`.

13. `}`
    Закриває весь блок `server`.

## Як разом працюють `frontend/src/App.js`, `nginx.conf` і `docker-compose.yml`

Ці три частини утворюють один повний ланцюжок запиту від браузера до бекенда.

### 1. Що робить frontend

У `frontend/src/App.js` є запит:

```js
axios.get('/api/tables')
```

Це означає, що frontend не звертається напряму до `http://localhost:3001`, а надсилає відносний запит на `/api/tables` у межах того самого хоста, з якого була відкрита сторінка.

### 2. Що робить nginx

У `nginx.conf` є правило:

```nginx
location /api/ {
    proxy_pass http://app:3001/;
}
```

Тому коли браузер відкриває сайт через nginx і frontend виконує `GET /api/tables`, nginx:

- приймає цей запит на `80` порт;
- бачить, що шлях починається з `/api/`;
- не шукає статичний файл;
- проксіює запит у контейнер `app` на порт `3001`.

### 3. Що робить Docker Compose

У `docker-compose.yml` сервіс `web` і сервіс `app` знаходяться в одній docker-мережі:

- `web` це nginx;
- `app` це NestJS;
- ім'я `app` у `proxy_pass http://app:3001/` працює саме тому, що це ім'я docker-сервісу.

Тобто nginx може звернутися до бекенда не через `localhost`, а через внутрішнє мережеве ім'я контейнера.

### 4. Як проходить запит крок за кроком

1. Користувач відкриває сайт у браузері через `http://localhost`.
2. Запит потрапляє в контейнер `web`, бо назовні відкритий порт `80`.
3. Nginx віддає фронтенд-статику з папки `client/`.
4. React-застосунок запускається в браузері.
5. `frontend/src/App.js` виконує `axios.get('/api/tables')`.
6. Запит знову приходить у nginx.
7. Nginx за правилом `location /api/` пересилає його в контейнер `app`.
8. NestJS обробляє запит і повертає JSON-відповідь.
9. Nginx повертає цю відповідь назад у браузер.
10. React отримує дані й рендерить список таблиць на сторінці.

### 5. Навіщо така схема зручна

Вона дає кілька практичних плюсів:

- frontend і backend працюють під одним хостом;
- frontend не треба знати окрему адресу бекенда;
- не треба відкривати порт бекенда назовні;
- простіше уникнути CORS-проблем;
- така схема ближча до реального продакшн-розгортання.

## Навіщо все це потрібно

Усі ці зміни разом вирішують одразу кілька задач:

### 1. Розвести відповідальності по папках і сервісах

- `backend/` містить API;
- `frontend/` містить сирцевий React-код;
- `client/` містить готовий build;
- корінь репозиторію містить docker/nginx-інфраструктуру.

Це зручніше для підтримки, ніж тримати все впереміш у корені.

### 2. Запускати весь стек однією командою

Ідея `docker-compose.yml` у тому, щоб одним підняттям отримати:

- MySQL;
- NestJS API;
- nginx для роздачі фронтенда й проксі на API.

Тобто локальне середовище стає ближчим до реального деплой-сценарію.

### 3. Автоматично готувати базу

Міграції запускаються перед стартом бекенда, тому схема БД підтягнеться автоматично без ручного окремого кроку.

Це потрібно, щоб:

- не забувати запускати міграції;
- швидше стартувати нове середовище;
- зменшити кількість помилок через неактуальну схему БД.

### 4. Віддавати frontend і API через одну точку входу

Через nginx браузер працює з одним хостом:

- статика приходить із `web`;
- запити `/api/*` автоматично летять у `app`.

Це спрощує:

- локальний запуск;
- маршрутизацію SPA;
- взаємодію фронтенда з бекендом;
- потенційні CORS-проблеми.

### 5. Зберігати дані між перезапусками

Завдяки `./mysql_db:/var/lib/mysql` база не скидається при кожному `docker compose down`.

Це потрібно, щоб:

- не втрачати тестові дані;
- не перестворювати все після кожного старту;
- мати більш реалістичну локальну БД.

## Підсумок

У поточних незакомічених змінах ти фактично зробив перехід від "окремого NestJS-проєкту" до більш повної локальної fullstack-структури:

- виніс бекенд у `backend/`;
- підготував Docker-оточення;
- додав MySQL і healthcheck;
- налаштував автозапуск міграцій;
- додав nginx як єдину точку входу;
- додав React-клієнт і його build;
- зібрав локальні артефакти для запуску й перевірки цього оточення.
